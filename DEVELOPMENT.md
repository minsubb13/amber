# Developing Amber

The plugin that users install is the `plugin/` directory (pi installs the repository as a pi package: the `pi` key of `package.json` points at `plugin/pi/`). Its hooks and scripts are written in TypeScript: sources live under `src/` and compile to the same `.cjs` paths under `plugin/`, so installs, the Node 20+ requirement, and every `scripts/record.cjs` path quoted in project instructions stay unchanged. Every `.cjs` file under `plugin/hooks`, `plugin/scripts` and `plugin/lib` is now compiled from `src/`; edit the `.cts` source. The plugin has no runtime dependencies; everything in `package.json` is for development only.

## Layout

- `src/` - TypeScript sources of the plugin (`.cts`, compiled by `tsconfig.json` into `plugin/`). `src/types/reset.d.ts` makes `JSON.parse` return `unknown` and `Array.isArray` narrow to `unknown[]`, so external data has to be checked before use.
  - `src/hooks/*.cts` and `src/scripts/*.cts` compile to the files the hosts and the hand-written `.cjs` files load, at their old paths. A ported module there keeps the exact `module.exports` of the file it replaced (names, order, constant values) while any CommonJS caller remains, binds the clock and runs the I/O, and leaves the rules to `src/lib/`.
  - `src/lib/*.cts` compile to `plugin/lib/*.cjs`, modules with one job each:
    - shared: the domain types (`types`, types only), value helpers that keep JavaScript's own outcome for values parsed from JSON (`guards`), globs (`glob`), the clock (`clock`);
    - run state and scope: plan rows (`plan`), the run state's rules (`progress-model`), the progress file (`progress-store`), git for the scope check (`git`), the scope check's rules (`scope`), the Codex rollout adapter (`codex-transcript`); the apply_patch parser stays in `src/hooks/patch-paths.cts`, where stage 2 ported it;
    - the hook: input checks (`hook-input`), Amber's home and state files (`state-store`), zones and worktrees (`zone`), contract loading (`contract`) and its rules (`contract-rules`), the ledger (`ledger`), the completion signal (`done-signal`), run ownership (`ownership`), the pre-approval phase's rules (`phase`) and its state, snapshot and exit row (`phase-store`), briefing and directive texts (`hook-text`) and their assembly (`briefing`), and one module per event: `session-start` (S0), `prompt-submit` (S1), `stop-gate` (S2), `skill-recorder` (S3), `enforcer` (E1). `src/hooks/amber-hook.cts` only reads stdin, picks the handler and writes its answer.
    - the recorder and the audit: `record-args` (usage text, unit commands, option words), `audit-report` (ledger counts and report lines), `audit-match` (a session's events against its rows, the session and check reports), `claude-transcript` (the Claude Code transcript adapter, beside `codex-transcript`). `src/scripts/record.cts` runs the recorder's commands and `src/scripts/audit.cts` reads the ledger, transcripts and reports.
    - Modules whose header says they work without I/O (`glob`, `plan`, `progress-model`, `phase`, `scope`, `guards`, `types`, `codex-transcript`, `contract-rules`, `hook-input`, `hook-text`, `record-args`, `audit-report`, `audit-match`, `claude-transcript`) do no I/O and read no clock.
  - Files compiled from `src/` are generated: their first line names the source to edit, and `.gitattributes` marks them `linguist-generated`, so pull request diffs fold them and a reviewer reads the `.cts` source.
- `plugin/pi/` - the pi host, hand-written like `plugin/hooks/hooks.json` and `run.sh`: `index.ts` is a pi extension that maps pi events onto the shared handlers in `plugin/lib` (`session_start`/`session_compact` -> S0, `input` -> S1, `agent_before_settle` -> S2, `tool_call` on `read` of a pi skill -> S3, `tool_call` on `bash`/`write`/`edit` -> E1), and `skills/amber-<name>/SKILL.md` are pointers to the shared skills under the names pi accepts. pi loads the TypeScript directly; it is outside the ordinary `tsconfig.json`, lint and parity tools. `runtime/` contains optional execution helpers, registered only after `session_start` sees `--amber-runtime`; the enforcement adapter stays separate. `npm run test:pi-runtime` checks the handwritten adapter/runtime types and drives the actual host in isolated mock tests (below).
- `tools/` - development tools in TypeScript (`.mts`, compiled by `tools/tsconfig.json` into `build/tools/`, which is not committed). `tools/qa/` holds the real-model QA tools, which drive an installed Claude Code or Codex CLI in throwaway zones and are run by hand, never in CI: `node build/tools/qa/model-qa.mjs <claude|codex> [scenario]` and `node build/tools/qa/host-probe.mjs`, after `npm run build:tools`.
- `test/` - the test suites, `node:test` files in TypeScript (`*.test.mts`, compiled by `test/tsconfig.json` into `build/test/`). They take the plugin under test from `AMBER_PLUGIN_DIR` (default `plugin/`), so the same suites drive any build, and load its modules through `test/support/plugin.mts`, typed by their sources in `src/`; `test/fixtures/` holds the inputs they read in place. `run.test.mts` drives the hook and the recorder through throwaway zones, one test per check; `audit.test.mts` and `codex.test.mts` cover the audit tool and the Codex host; `characterization.test.mts` pins the current behavior of paths the other suites do not reach; `characterization-s2.test.mts` does the same for the branches of the stage 2 modules by calling their exports directly, `characterization-s3.test.mts` for the hook, mostly by starting it with crafted inputs, and `characterization-s4.test.mts` for the recorder and the audit tool on small zones, ledgers and transcripts; `model-qa.test.mts` tests the QA tools' helpers.

## Scripts

Run `npm ci` once, then:

- `npm run typecheck` - type-check `src/`, `tools/` and `test/`.
- `npm run lint` - typescript-eslint `strictTypeChecked` plus exhaustive switches, no type assertions, no non-null assertions, no `@ts-` directives, no `any`; zero warnings allowed. In `src/` it also forbids asynchronous I/O and process APIs, `async`/`await`, promises, timers, and signal handlers, with `node:fs` bound as `fs` and `node:child_process` as `childProcess` so every use is visible to the rule: the plugin is a set of short synchronous programs (only the hook reads stdin through stream events), and keeping the port that way leaves nothing the parity capture cannot observe, such as output released before a pending write or signal handling. In `test/`, `node:test`'s `test`, `describe`, `it` and `suite` are known-safe calls for `no-floating-promises`: node:test runs a registered test without anyone awaiting the promise it returns.
- `npm run format:check` / `npm run format` - Prettier on `src/`, `tools/` and `test/` (not `test/fixtures/`, which the suites read byte for byte).
- `npm run build` - compile `src/` into `plugin/`, then put the generated-file header above tsc's `"use strict"` line (`tools/header/`). The committed output must equal a fresh build (`npm run build && git diff --exit-code`).
- `npm test` - build the tools and the suites, then run every suite against `plugin/` (or `-- --plugin <dir>`) in one serial `node --test` process.
- `npm run coverage` - line and branch coverage of `plugin/hooks/*.cjs`, `plugin/scripts/*.cjs` and `plugin/lib/*.cjs` under every suite, child processes included, with the uncovered line ranges per file. `-- --branches` also lists every branch no suite took; `-- --plugin <dir>` measures another copy, such as the reference.
- `npm run parity -- --ref <rev>`, `npm run parity:real -- --ref <rev>`, `npm run parity:selftest -- --ref <rev>`, `npm run parity:tests -- --ref <rev>`, `npm run parity:legacy -- --ref <rev>` - see below.

## Optional pi runtime tests

Prerequisites: existing development dependencies (`npm ci`), Node 24+ for native TypeScript test execution (verified on v24.13.1), and pi 1.3+ on PATH (verified on 1.3.0). The plugin's ordinary Node 20+ requirement is unchanged; the extra Node requirement belongs only to this test runner. No runtime dependency or peer installation is needed.

```sh
npm run test:pi-runtime
```

The command first strict-typechecks `plugin/pi/index.ts` and `plugin/pi/runtime/*.ts` against host-supplied declarations, then runs `test/pi-runtime/e2e/*.test.ts` directly with node:test. Managed pi installs are discovered through `PI_MANAGED_INSTALL_ROOT` (or `~/.pi/agent/install/current-version`). For another installation layout, set `PI_RUNTIME_PACKAGE_ROOT` to the installed `@earendil-works/pi-coding-agent` package directory. The typecheck uses a disposable temporary tsconfig, not a new dependency or a change to installed pi. Ordinary `npm run typecheck` and lint do **not** check handwritten pi sources; the runtime harness's `.ts` fixtures are transpiled by Node, not covered by the strict `.mts` test project. Prettier checks the new tests/tooling with the existing format command. Node may emit a harmless MODULE_TYPELESS_PACKAGE_JSON warning for the native `.ts` tests; no package-wide module mode was changed.

The harness starts real pi RPC processes with loopback OpenAI Responses/Anthropic Messages SSE mocks, dummy keys and isolated temporary HOME, PI_CODING_AGENT_DIR and AMBER_HOME. It constructs a small environment instead of inheriting real auth variables; disables discovered extensions/skills/context, MCP, themes, project approval, catalog networking, compaction and cache warming; and writes sessions only inside its temporary directory when testing persistence. Never replace these endpoints with provider URLs. This command sends no real provider requests and does not read real auth or modify real settings/session files. Do not run the standalone real-priority probe: both authorized requests were already consumed.

The 22 standalone production behavior tests and two feasibility direction checks from read-only source `814562b` are adapted to the full Amber extension. The two direction checks now also verify attribution and forbidden-write enforcement. Additional cases prove prompt-free CLI flag lifecycle, default-off payload/registration/recovery absence, standalone conflicts in both load orders, reload persistence and incomplete-work completion gating with/without native retry. Legacy `src/switch-model.ts`/`src/fast.ts` selectors in the ported cases are translated by the harness to the full Amber extension, never loaded from the source repository.

Opt-in/manual use is `pi -e ./plugin/pi/index.ts --amber-runtime`. Without the flag no helper is registered. `/fast [on|off]` controls only OpenAI agent-loop requests; `switch_model` has a fixed two-model allowlist and optional thinking level, session transcript changes, and no settings persistence. Remove the standalone package/files yourself before enabling this runtime (README migration instructions); Amber refuses the new runtime on a conflicting tool or command and never uninstalls or edits settings. Keep all future tests loopback-only. Completed tier is authoritative: quoted corrected standalone HTTP200 receipt reported `default`, so actual priority, speed and quota effects remain unverified; raw quoted receipts and provenance are under `docs/pi-runtime/`.

## Parity

The port must not change anything Amber shows to the outside: the stdout, stderr, and exit code of every entry point (hook JSON for each host and every message included), the `.amber/` files of a zone, the ledger rows, and the session state files. Three commands compare a reference build with the working tree's `plugin/`. The reference build is `plugin/` of `<rev>` (default `origin/main`) - code, `run.sh`, `hooks.json`, skills, and references - with one exception taken from the working tree: the two manifests, whose version is the one outside-visible change every release makes on purpose (it reaches each ledger row as `plugin_version`). The list is `SHARED_WITH_CANDIDATE` in `tools/parity/workspace.mts`. Both builds run the working tree's suites from `build/test`.

- `parity` runs every suite against both builds. A preload (`NODE_OPTIONS=--require`, `tools/parity/capture.cts`) acts in each product process the suites start (and records the calls a suite makes into plugin modules it requires, with their arguments): before the product module runs, it re-runs the same command (same node flags, script path, arguments, environment, and inherited stdin) as a child with stdout and stderr piped, so whatever reaches file descriptors 1 and 2 is recorded whichever channel wrote it; it also records argv, the stdin the product read, the exit code, appended ledger bytes, changed state files, and the zone's `.amber` files afterwards, then forwards the output and ends the way the child ended (exit code or signal). The normalized records are compared as multisets. Temporary directory names and git commit dates are made deterministic at the source; the remaining normalization rules and the reason for each are listed in `tools/parity/normalize.mts`. The last line reads `PARITY invocations=<n> differences=<d>`.
- `parity:real` replays this machine's own records through both builds in scratch zones and scratch Amber homes: every `audit.cjs` command over a ledger snapshot, real tool calls from Claude Code transcripts and Codex rollouts through E1 under each zone's contracts, the S0 briefing of every contract, and `unit init` of every plan. The real ledger and transcripts are only read, and nothing from them is written to the repository. It needs those records, so it runs locally, not in CI. The last line reads `REAL audit=<n> e1=<n> s0=<n> plans=<n> differences=<d>`.
- `parity:tests` compares two sets of suites instead of two builds: the legacy CommonJS suites of `<rev>` (its `plugin/tests`, from before the suites moved to `test/`) and the suites of `test/`, both against the working tree's `plugin/`. It requires the same test names, both sets passing, and the same product invocations under the same normalization, with each side's fixtures directory read as one. Because both sides run one build, what the product read also counts as input here: every file text, sorted directory listing, existence check, stat (kind and age in whole hours) and git output, in product processes and during the suites' calls into plugin modules they require (the plugin's own files left out). Between two builds which files a build reads is its own business, so the other commands leave the reads out. The last line reads `TESTS names=<legacy>/<new> same-names=<yes|no> failed-suites=<n> invocations=<legacy>/<new> differences=<d>`.
- `parity:legacy` runs the legacy suites of `<rev>` against `<rev>`'s own build and against the working tree's `plugin/`: both must pass with the same product invocations. It compares the final build with a revision from before the port on that revision's own tests. The last line reads `LEGACY tests=<ref>/<candidate> invocations=<n> failed-suites=<n> differences=<d>`.
- `parity:selftest` applies four outside-visible mutations to a candidate copy (one character of a briefing, a refusal exit code, an E1 decision, a `progress.json` value) and requires each to be reported, the E1 one by the real-record replay as well. A control that only moves one message from `process.stdout.write` to `fs.writeSync(1, ...)` must report no difference, and a probe that makes `record.cjs` start a grandchild writing to the inherited stdout must be reported by the record comparison itself.

## Porting a module

Each module moves in the same order, so that the comparison has something to bite on before the code changes:

1. List what the module shows to the outside: its exports, the messages it throws or prints, the files it reads and writes with their shape and key order, and the commands it runs.
2. Measure the original's branch coverage (`npm run coverage -- --plugin <reference> --branches`) and pin every branch the suites do not take with a characterization test that asserts what the original returns or throws today, malformed input included, or record why it cannot be reached.
3. Design the types: boundary input arrives as `unknown` and passes a check before it becomes a domain type; closed sets of values are unions closed by exhaustive switches; rules without I/O live apart from the code that reads files, runs git, or reads the clock. A check never accepts or rejects more than the original did - where the original trusted a file or read a foreign format loosely, the source says so.
4. Write the `.cts` source, build, and run `npm test`, `npm run parity`, `npm run parity:selftest`, and `npm run parity:real` against the previous stage. Deliberately break one outside-visible value in the compiled output and confirm the comparison reports it, then rebuild.
